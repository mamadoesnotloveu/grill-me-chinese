# 决策状态与来源协议

本协议防止把助手自己的建议篡写为用户决定。每一项产品状态都必须有唯一状态和来源。

## 状态

| 状态 | 使用条件 |
|---|---|
| 用户已确认 | 用户明确陈述决定、明确选择一个选项，或明确表示接受紧邻的具体建议 |
| 助手建议、未确认 | 出现在建议答案、推荐、示例或助手总结中，但用户没有接受 |
| 模型推断、未确认 | 根据上下文推断，尚未得到用户确认 |
| 待确认 | 需要用户选择、补充或消除歧义 |
| 已延期 | 用户明确延期，并记录影响和重访条件 |
| 已否决 | 用户明确拒绝 |
| 已被替代 | 过去已确认、后来被新决定取代；同时链接当前有效决定 |

## 晋升规则

只有以下用户表达可以产生“用户已确认”：

- 直接陈述，例如“第一版使用 SQLite”。
- 回答当前问题并明确选择，例如“选 B，因为……”。
- 明确接受紧邻建议，例如“同意你的建议”“按这个方案”“是，默认关闭”。

以下表达绝不构成接受：

- `继续烤`、`继续`、`下一题`、`深入这个问题`。
- `阶段总结`、`还有多远`、`暂停`、`出炉`。
- 沉默、跳过回答、回答另一个问题或只改变强度。
- 助手自己重述、推荐、举例或在总结中写出的内容。

“可以”“好”“是”指向不清楚时，先询问它接受哪一项，不得晋升状态。

## 来源记录

内部每项至少记录：

```text
ID | 状态 | 内容 | 来源角色 | 来源轮次 | 依据 | 替代关系
```

- 用户已确认项的来源角色必须是用户，并能指向用户轮次中的明确表达。
- 助手建议的来源角色必须是助手，即使后来被多次复述，也不能自行晋升。
- 用简短忠实转述记录来源；不要伪造逐字引文。
- 新决定冲突时，把旧项标为已被替代，不删除历史。

## 决策校对

按以下结构输出：

```markdown
### 用户已确认
- D1 ……（来源：用户第 N 轮）

### 助手建议，尚未确认
- P1 ……（来源：助手第 N 轮建议答案）

### 模型推断，尚未确认
- I1 ……（依据：……）

### 待确认 / 已延期 / 已否决 / 已被替代
- ……

请回复“确认以上状态”，或写明需要纠正的编号。
```

校对只验证状态记录，不表示用户接受“助手建议”栏目。即使用户回复“确认以上状态”，也只确认分类和记录准确；除非用户点名接受某个建议编号，否则建议仍为未确认。

决策校对是一道硬门：输出校对后立即结束该回复，不得附带下一问题、建议答案、“为什么重要”、下一步或继续邀请。等待用户确认或纠正；确认后仅在用户没有同时要求暂停或结束时恢复访谈。

## 最终交付门

- 只有“用户已确认”可以写成硬需求或既定决定。
- 助手建议放入“建议方案，尚未确认”。
- 模型推断放入“推断，尚未确认”。
- 待确认、延期、否决和替代历史分别列出。
- 若一项内容无法追溯来源，降级为模型推断，不得写成用户决定。
- 生成 Codex 开发提示词时，未确认内容必须位于“待确认/建议”部分，并明确禁止实施代理自行当作产品事实。
